This workflow tells you when it stopped working

Most automation failures are not red errors. They are runs that finish green and produce nothing, and the client notices before the builder does. This sample is built for that case.

What is inside

Run receipt on every run Each run writes one row to a Run Log sheet: when it fired, which record it handled, what it did, and whether it succeeded. A run that fires and writes zero is visible as zero, not as success.
Failure branch, not a silent stop When a node fails, the error output routes to a Slack message and a FAILED row in the same log. The failure path is wired, not implied.
Retries on network calls HTTP nodes retry three times with a five second gap before they are allowed to fail.

Tested, not described

The workflow was imported into n8n 2.35.7 and executed as a twin build. 13 nodes ran, the receipt node produced 1 row in the Run Log, and the static checks scored 9/9. The four cases below are the ones it was run against.

CaseWhat happensResult
Four due rowsTwo true branches, two false, four dedup keyspass
Zero rowsNothing sent, and no SUCCESS row writtenpass
Same record twiceDedup keeps one, no double sendpass
Provider returns an errorFailure branch fires, FAILED row writtenpass

The failure case is a real run where the provider returns an error, not a description inferred from the export.

Acceptance test you can run yourself

Import the file, connect your own sheet, then send one row that is due and one that is not. You should get one message, one Run Log row for the due record, and nothing for the other. Then break a credential on purpose and run it again: you should get a FAILED row and a Slack message, not silence.
